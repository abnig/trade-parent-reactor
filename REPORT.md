# Flyway Migration Foundation

## Existing DDL Review

`v1.sql` is the authoritative current-schema export. It contains six Spring Batch tables (`batch_job_instance`, `batch_job_execution`, `batch_job_execution_context`, `batch_job_execution_params`, `batch_step_execution`, and `batch_step_execution_context`); application tables (`ledger_balances`, `ledger_records`, `trade_records`, `mutual_fund_broker_account`, `mutual_fund`, `mutual_fund_txn`, and `mutual_fund_value`); Spring AI chat memory; and the `vector_store` table with its `spring_ai_vector_index` HNSW index.

The export uses `uuid_generate_v4()` and `vector`/`vector_cosine_ops`, requiring `uuid-ossp` and pgvector. It also contained local `OWNER TO postgres` and `GRANT ... TO postgres` statements, redundant named NOT NULL export constraints, and a broker-account default that references a sequence not created by the export.

## Migration Layout

- `V1__extensions.sql`: `uuid-ossp` and pgvector extensions.
- `V2__spring_batch_schema.sql`: Spring Batch metadata schema.
- `V3__application_schema.sql`: business and mutual-fund tables.
- `V4__spring_ai_schema.sql`: chat memory, vector store, and HNSW vector index.

This separation establishes ordering between extensions, framework infrastructure, application tables, and Spring AI/vector storage. The next version is reserved for `V5__create_app_user.sql`; no user, role, ownership, authentication, or security object was created.

## DDL Normalization

The migrations intentionally omit environment-specific ownership/grant commands and export comments. Redundant generated named NOT NULL constraints were converted to ordinary column `NOT NULL` declarations. Meaningful primary keys, foreign keys, unique constraints, defaults, and the `trade_records` trade-type check were retained.

`v1.sql` lists the six Batch tables but not the three PostgreSQL sequences required by the repository's Spring Batch 6.0.3 schema (`batch_step_execution_seq`, `batch_job_execution_seq`, and `batch_job_instance_seq`). V2 includes those sequences exactly as supplied by Spring Batch 6.0.3 so a fresh database is compatible with the running Batch version. Verify their presence before baselining an existing database; do not baseline a schema that lacks required Batch objects.

## Broker Account ID Strategy

The current export references the missing `broker_account_broker_account_id_seq`. `MutualFundBrokerAccountRepositoryImpl.save()` omits `broker_account_id`, so the database must generate it. V3 uses `BIGINT GENERATED BY DEFAULT AS IDENTITY`: it generates IDs for existing repository inserts while retaining legacy sequence-default behavior that permits an explicit ID if one is ever supplied. No uncreated sequence is referenced.

## Extensions and Spring AI

V1 creates `uuid-ossp` before V4 uses `uuid_generate_v4()`, and creates pgvector before V4 uses `VECTOR` and `vector_cosine_ops`. The PostgreSQL server must have pgvector installed and the migration role must be permitted to create these extensions.

No Spring AI PgVector/chat-memory dependency, bean, or initialization property is configured in the MCP module; the exported AI tables are therefore not auto-created by the checked-in application. V4 is their schema owner. Vector dimension is intentionally unspecified because `v1.sql` uses the unconstrained `vector` type and no application configuration defines a dimension.

## Existing Database Baseline

Do not run V1–V4 on a populated database. First verify the expected tables, key foreign keys, Batch sequences, `uuid-ossp`/`vector` extensions, and the broker-account ID default/sequence or identity behavior. For example, run this read-only preflight query against the target database and investigate every `NULL` or `false` result before baselining:

```sql
SELECT
    to_regclass('public.batch_job_instance') IS NOT NULL AS batch_job_instance_exists,
    to_regclass('public.batch_job_execution') IS NOT NULL AS batch_job_execution_exists,
    to_regclass('public.batch_step_execution') IS NOT NULL AS batch_step_execution_exists,
    to_regclass('public.batch_job_instance_seq') IS NOT NULL AS batch_job_instance_seq_exists,
    to_regclass('public.batch_job_execution_seq') IS NOT NULL AS batch_job_execution_seq_exists,
    to_regclass('public.batch_step_execution_seq') IS NOT NULL AS batch_step_execution_seq_exists,
    to_regclass('public.mutual_fund_broker_account') IS NOT NULL AS broker_account_exists,
    to_regclass('public.mutual_fund') IS NOT NULL AS mutual_fund_exists,
    to_regclass('public.mutual_fund_txn') IS NOT NULL AS mutual_fund_txn_exists,
    to_regclass('public.mutual_fund_value') IS NOT NULL AS mutual_fund_value_exists,
    to_regclass('public.trade_records') IS NOT NULL AS trade_records_exists,
    to_regclass('public.ledger_records') IS NOT NULL AS ledger_records_exists,
    to_regclass('public.spring_ai_chat_memory') IS NOT NULL AS chat_memory_exists,
    to_regclass('public.vector_store') IS NOT NULL AS vector_store_exists,
    EXISTS (SELECT 1 FROM pg_extension WHERE extname = 'uuid-ossp') AS uuid_ossp_exists,
    EXISTS (SELECT 1 FROM pg_extension WHERE extname = 'vector') AS vector_exists;
```

Then run REST once with the `flyway-baseline` profile, for example after building the REST artifact:

```text
SPRING_PROFILES_ACTIVE=flyway-baseline \
java -jar trade-rest/target/trade-rest-0.0.1-SNAPSHOT.jar
```

The profile temporarily sets `baseline-on-migrate=true`; standard configuration has it set to `false`. Flyway creates its own `flyway_schema_history` baseline entry at version 4 and does not recreate, truncate, drop, or otherwise change existing application data. Do not manually alter that table.

## Fresh Database

On an empty PostgreSQL database, normal REST startup applies V1 through V4 in order. `flyway_schema_history` records each version, description, checksum, execution time, and success status. Subsequent startup validates checksums and does not reapply completed migrations. `clean` is disabled.

## Schema Ownership and Framework Initialization

REST is the migration owner. Batch and MCP are configured with `spring.flyway.enabled=false`, `spring.batch.jdbc.initialize-schema=never`, `spring.sql.init.mode=never`, and `spring.jpa.hibernate.ddl-auto=none`. REST has Flyway enabled and also uses Hibernate `ddl-auto=none`. This prevents Hibernate, Spring Batch, or SQL initialization from competing with Flyway; Spring AI has no configured schema initializer.
