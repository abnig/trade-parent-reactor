### Transaction and concurrency boundaries

Portfolio CRUD has no encompassing application `@Transactional`: parent check, single INSERT/UPDATE/DELETE, then reread are separate JDBC calls. SQL includes ownership in mutations so a stale Java parent lookup alone cannot authorize cross-owner writes. The write can commit before a failing reread. List and count are separate reads; no optimistic lock/version or idempotency key. Concurrent edits are last-write-wins; uniqueness/FK failures return generic400. Changing funds/transactions can be blocked by same-fund order references.

Registration service and repository participate in a single Spring transaction, including optional recovery enrollment. Profile service owns the transaction; repository requires it and locks the user row before eligibility/password/version checks and mutations. Email changes clear recovery state but do not increment credential_version. A failed duplicate email update rolls back profile/hint changes. [RegistrationService.java:22](../../trade-rest/src/main/java/com/trading/service/RegistrationService.java#L22), [UserProfileService.java:28](../../trade-rest/src/main/java/com/trading/profile/UserProfileService.java#L28), [JdbcUserProfileRepository.java:31](../../trade-repository/src/main/java/com/trading/repository/impl/JdbcUserProfileRepository.java#L31)

Recovery service itself is not globally transactional. Repository enrollment, challenge attempt, token issuance and completion each have explicit transaction boundaries. Rate counters and challenge creation/purge are separate operations. Issuance locks/rechecks account/version, consumes challenge conditionally, replaces the user's existing token. SMTP runs afterward: reset send failure revokes the token and returns503; reminder send failure is swallowed for account privacy. Complete locks user, deletes a still-valid token atomically, updates password and increments both versions, clears challenges/tokens. Concurrent completion cannot use one token twice. **T** H2/PostgreSQL tests exercise replay, locking and rollback. [JdbcPasswordRecoveryRepository.java:87](../../trade-repository/src/main/java/com/trading/repository/impl/JdbcPasswordRecoveryRepository.java#L87), [JdbcPasswordRecoveryRepository.java:101](../../trade-repository/src/main/java/com/trading/repository/impl/JdbcPasswordRecoveryRepository.java#L101), [PasswordRecoveryService.java:84](../../trade-rest/src/main/java/com/trading/recovery/PasswordRecoveryService.java#L84)

Batch delete is a separate step transaction preceding chunk transactions. Earlier committed chunks and delete are not rolled back when a later chunk/job fails. JPA `saveAll` participates in configured chunk transaction. Broad skip rules can recover some item failures but do not imply whole-file atomicity. MCP queries have no application transaction spanning multiple calls and no retry layer.

all rows, stores immutable bytes and invokes the existing CoinImportService. Its
manually registered datasource singleton is borrowed; context close does not
close REST's Hikari pool. Coin configuration is deliberately not a scan candidate.

[CoinUploadOptions](../../trade-rest/src/main/java/com/trading/upload/CoinUploadOptions.java)
validates request metadata and builds options with the session owner.
[ZerodhaTransactionUploadService.importFile](../../trade-rest/src/main/java/com/trading/upload/ZerodhaTransactionUploadService.java)
bounds bytes/concurrency, maps safe failures and returns a completed receipt.
[CoinUploadException](../../trade-rest/src/main/java/com/trading/upload/CoinUploadException.java)
contains only public messages/codes, without private database exception causes.
GlobalExceptionHandler preserves structured per-record field errors and HTTP status.

`trade-rest/pom.xml` consumes `trade-batch:coin-library` and Batch core only;
`trade-batch/pom.xml` attaches that limited ordinary JAR at process-classes. This
is the narrow module dependency required by the user's endpoint integration.
[CoinUploadPostgresIntegrationTest](../../trade-rest/src/test/java/com/trading/upload/CoinUploadPostgresIntegrationTest.java)
verifies REST has no root Job/JobRepository beans, that the pool stays open, and
that only the Coin job writes through real HTTP and PostgreSQL paths.
